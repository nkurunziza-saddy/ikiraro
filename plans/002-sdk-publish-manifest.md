## Why this matters

`@ikiraro/sdk` is published to npm (currently 0.4.1). Its local `package.json` declares `dependencies` on `@ikiraro/engine`, `@ikiraro/renderer`, and `@ikiraro/runtime` via `workspace:*`. But `@ikiraro/renderer` and `@ikiraro/runtime` are `"private": true` and do **not exist on npm**. When changesets publishes the next version, the `workspace:*` ranges get rewritten to concrete versions of packages nobody can install — `npm install @ikiraro/sdk` would fail for every consumer. The published 0.4.1 on npm has **no `dependencies` field at all** (verified via `npm view @ikiraro/sdk dependencies` → empty), which works because the sdk's tsup config bundles all `@ikiraro/*` code into `dist/` (`noExternal: [/^@ikiraro\//]`). The local manifest has drifted from the publishable shape; this plan restores it deliberately by moving the workspace deps to `devDependencies`.

## Current state

- `packages/sdk/package.json` (excerpt — the problem):

  ```json
  "dependencies": {
    "@ikiraro/engine": "workspace:*",
    "@ikiraro/renderer": "workspace:*",
    "@ikiraro/runtime": "workspace:*"
  },
  "devDependencies": {
    "@types/react": "^19.2.14",
    "@types/react-dom": "^19.2.3",
    "tsup": "^8.5.0",
    "typescript": "^6.0.3"
  },
  ```

- `packages/sdk/tsup.config.ts` (excerpt — why the deps are not needed at runtime):

  ```ts
  external: [ "react", "react-dom", "react/jsx-runtime", "three", "@react-three/fiber", "@react-three/drei", "effect", "@mediapipe/tasks-vision" ],
  noExternal: [/^@ikiraro\//],
  ```

  All `@ikiraro/*` source is compiled into `dist/index.js`, `dist/components.js`, `dist/engine.js`, and the worker bundle. Everything a consumer needs at runtime is either in `dist/` or declared in `peerDependencies`.

- `packages/renderer/package.json` and `packages/runtime/package.json` both have `"private": true`. `@ikiraro/engine` IS published (0.2.0 on npm), but it's also bundled by tsup, so it does not need to be a runtime dependency either.

- Published manifest ground truth: `npm view @ikiraro/sdk@0.4.1` shows `peerDependencies` only — no `dependencies`.

- Turbo's task graph (`turbo.json`: `build.dependsOn: ["^build"]`) resolves workspace topology from `dependencies` **and** `devDependencies`, so moving these to `devDependencies` does not break build ordering.

## Steps

### Step 1: Move workspace deps to devDependencies

In `packages/sdk/package.json`, delete the `dependencies` block and merge its three entries into `devDependencies`:

```json
"devDependencies": {
  "@ikiraro/engine": "workspace:*",
  "@ikiraro/renderer": "workspace:*",
  "@ikiraro/runtime": "workspace:*",
  "@types/react": "^19.2.14",
  "@types/react-dom": "^19.2.3",
  "tsup": "^8.5.0",
  "typescript": "^6.0.3"
}
```

Then run `bun install` to refresh the lockfile.

**Verify**: `bun install` → exit 0. `git diff packages/sdk/package.json` shows only the dependency move.

### Step 2: Confirm the sdk still builds and bundles workspace code

```
cd packages/sdk && bun run build
```

**Verify**: exit 0, and `grep -c "SignAllRecognizer\|createIkiraro" dist/index.js` → at least 1 (workspace code is bundled in, not imported).

### Step 3: Confirm the publishable artifact is dependency-free

```
cd packages/sdk && npm pack --dry-run 2>&1 | tail -20
```

**Verify**: pack succeeds and includes `dist/`, `skill/`, `bin/`, `README.md`. Then confirm no runtime deps remain: `node -e "const p=require('./package.json'); console.log(JSON.stringify(p.dependencies ?? null))"` (run in `packages/sdk/`) → prints `null`.

### Step 4: Full workspace verification

```
bun run check-types && bun run test
```

**Verify**: both exit 0.

## Maintenance notes

- **Watch in review**: any future PR that adds a `dependencies` entry to `packages/sdk/package.json` re-introduces this bug unless the dep is genuinely public and unbundled. Consider a comment in the manifest is not possible (JSON), so the knowledge lives in this plan and ideally in a future CLAUDE.md.
- If renderer/runtime are ever published as standalone packages, the right shape flips: deps become real `dependencies` and `noExternal` narrows. That is a deliberate architecture change, not a cleanup.
